# Architecture

## Goals
- Work fully offline on a phone (installed PWA); data never leaves the device unless the user exports it.
- A plan is a JSON document any author (coach, AI, the athlete) can produce and the app can validate.
- Small, boring stack; layers that let a future sync backend and multi-user mode be added without rewriting the UI.

## Stack
Next.js 16 (App Router, Cache Components, Turbopack) · React 19 · Tailwind v4 · Dexie 4 (IndexedDB) · zod 4 · vitest. No UI kit, no global state library.

## Layers and dependency rule
```
src/app        routes only: metadata + one feature component. No logic.
src/features   UI + hooks per feature (plans, workout, today, history, exercises, settings, bootstrap)
src/infra      adapters: db (Dexie repos), catalog (fetch + search), pwa (SW registration)
src/domain     pure TypeScript: plan schema, set expansion, progression rule, record types. Unit tested.
src/shared     ui primitives, small helpers (ids, format)
src/content    bundled plan JSON (+ test that validates them against schema and catalog)
```
Allowed imports: `app → features | shared`, `features → infra | domain | shared | content`, `infra → domain | shared`, `domain → (nothing)`. ESLint does not enforce this yet (roadmap item).

## Data model (IndexedDB `gymbro`, v1)
| Table | Key | Indexes | Notes |
|---|---|---|---|
| `plans` | `id` (plan slug) | `updatedAt, archivedAt` | `doc` = validated Plan; `origin` bundled/imported; `userEdited` guards re-seeding |
| `workouts` | uuid | `planId, status, startedAt, [planId+sessionId]` | one row per started session; snapshot `sessionName` |
| `setLogs` | uuid | `workoutId, exerciseKey, completedAt, [exerciseKey+completedAt], [workoutId+exerciseKey]` | one row per set; `exerciseKey` = catalog id or `custom:<key>` so history joins across plans |
| `settings` | `key` | | `activePlanId`, future prefs |

Why `exerciseKey` and not plan-local keys: when the next plan reuses "barbell bench press" (catalog `0025`) the previous weights must show up even though the plan id changed.

## Core flows
- **Bootstrap** (`features/bootstrap`): on load, seed bundled plans (idempotent; refreshes untouched copies when the JSON hash changes), set default active plan, apply theme.
- **Start session** → `workoutsRepo.start` → `/workout/[id]`. One active workout per plan; starting another asks to abandon.
- **Log a set** → `setLogsRepo.upsertSet` (idempotent on workout+exercise+setIndex). The row shows previous performance (`lastPerformance`) and the suggestion from `domain/progression/suggestNext` (double progression).
- **Rest timer** appears after a completed set using exercise `restSec` or block `restSec`.
- **Guide**: catalog JSON (856 KB, English only) fetched once and cached by the SW; GIF/JPG loaded from the dataset host on demand and cached (LRU 400).

## Rendering strategy
All routes are static shells (Cache Components). Client components read IndexedDB after hydration via `useLiveQuery`. `useParams`/`usePathname` are wrapped in `<Suspense>` so dynamic routes still prerender a shell. Nothing runs on the server at request time, which keeps the app deployable as static hosting later if desired (`output: "export"` is not enabled yet because `manifest.ts` and PPR are used; switching is a one-line change plus moving the manifest to `public/`).

## PWA / offline
- `src/app/manifest.ts` + `public/icons/*` (generated by `scripts/make-icons.mjs`).
- `public/sw.js` hand-written: network-first navigations with shell fallback, cache-first `/_next/static`, stale-while-revalidate `/data/*`, cache-first media. Registered only in production. Bump `VERSION` to invalidate.
- Known limit: first load of a route must happen online once before it works offline; precache list in `sw.js` covers the main tabs.

## Exercise dataset
`scripts/build-exercise-catalog.mjs` downloads `hasaneyldrm/exercises-dataset` (MIT for data) and writes a slim English catalog (`id, name, bodyPart, target, equipment, secondaryMuscles, mediaId, steps`). Media (© Gym visual, 180×180) stays remote: `MEDIA_BASE/videos/<id>-<mediaId>.gif`, override with `NEXT_PUBLIC_EXERCISE_MEDIA_BASE` to self-host. Non-commercial personal use; keep attribution.

## Extension points (designed, not built)
- **Sync / coach upload**: repos are the seam. Add `infra/sync/` that pushes/pulls `plans`, `workouts`, `setLogs` with `updatedAt` + device id; UI stays unchanged. Plans already carry `meta.source` and `meta.author`.
- **Multi-user**: add `ownerId` to records in Dexie v2 and scope queries; auth lives in `app/(auth)` with a server adapter.
- **Plan editing in-app**: plan JSON is the model; an editor is a form over `PlanSchema`.
- **Exercise swaps**: in a running workout each exercise with `alternatives` gets a "⇄ جایگزین" picker (`features/workout/exercise-swap.tsx`). The choice is stored on the workout (`Workout.swaps[exerciseKey] = catalogId`); a plan-wide default ("my gym has no hack squat") is stored in `settings` under `swaps:<planId>` (`infra/db/swaps-repo.ts`). The performed exercise is `applySwap()` (`domain/workout/swap.ts`): same prescription, the alternative's catalog id, so logs, "previous" and load suggestions follow the alternative's own history. Sets already logged in the workout move with a swap. No index change, so no Dexie version bump.
- **Localization**: the UI is Persian and RTL (`<html lang="fa" dir="rtl">`, Vazirmatn font, Jalali dates with Latin digits via `LOCALE` in `shared/lib/format.ts`). UI strings are inline; closed vocabularies (catalog body parts/equipment/muscles, session kinds, block types, plan sources, workout status) are mapped in `shared/i18n/fa.ts`. Plan names use `nameFa` when present (`faName()`); free plan text and the exercise catalog stay English and render with `dir="auto"`/`dir="ltr"`. An English toggle would move the inline strings into a `shared/i18n` dictionary.

## Conventions
- Files kebab-case; components PascalCase exports; hooks `use-*.ts`.
- Client components start with `"use client"`; pages stay server components unless they need params.
- Tests next to domain code in `__tests__`; run with `npm run test`.
- Commit messages: imperative, one topic each.
